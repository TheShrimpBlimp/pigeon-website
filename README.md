# Pigeon download and setup site

Edit `index.html` and `site.css` here. The current offline sample tool stays in
`../pigeon/`; firmware packaging lives in `../make_site.py`.

From the project root, build with:

```sh
.venv/bin/python web/make_site.py build/pigeon.fwsc 0.1-beta-candidate web/site/dist
```

`dist/` contains the complete static site, current firmware, matching source,
licences, installer, guides, and browser sample tool. Imported user audio is not
included. The landing page uses local fonts and no external scripts.

Serve `dist/` with a loopback-only static server to preview locally. For USB MIDI,
use desktop Chrome or Edge at localhost or on HTTPS. Firmware upload remains a
user-initiated action; visiting the site does not write to a device.

The Sites project identity is retained in `.openai/hosting.json`. Its initial
hosted audience is private. The main firmware Git checkout is separate from the
site's hosting checkout.

## Install counts

The hosted build includes a Worker API and a D1 database (`DB`).
`worker/index.js` serves `/api/installs`; other paths use the asset binding.
`drizzle/0000_installs.sql` is the schema migration. GET returns the total and
counts by firmware SHA-256. Each successful install gets a random event UUID;
retries with the same UUID count once, and reinstalls get new UUIDs.
No samples, MIDI data, device identity, account ID, or IP address are stored in
this database. Platform operational logs are separate. Reports are generated by
the browser, can be forged, and do not measure unique hardware. Earlier CLI
installs are not backfilled. Offline events retry when online; clearing browser
storage before delivery loses those reports. Statistics never block flashing.
The existing private Site audience continues to apply to this API and website.
Build output now uses `dist/client/` assets and `dist/server/` Worker code.
